# 5 点以上思考（验收第 9 点）

> 这 6 点都是在题目要求之外、但真实落地必须考虑的问题。
> 前 3 点偏业务和数据，后 3 点偏工程和运维。

---

## 1. 数据资产化：下游只要标准 JSON，但系统内部必须保留冗余信息

题目要求的是最终 JSON，但实际抽取出来的信息远多于输出字段：原始文件、OCR 原始响应、表格、字段证据、置信度、匹配过程、人工修正，这些都不在下游 schema 里，却不能丢。

我的做法是：原始文件和派生结果按 `sha256` 进资产库，结构化的内部信息进 SQLite，最终 `output.json` 只是内部记录的一个投影。这样同一份材料可以审计、可以重放、可以换模型重跑，也可以作为评测样本。**冗余不是浪费，是数据资产。**

---

## 2. 人工复核闭环：LLM 的输出不可能完全对上标准 schema

即使引入 LLM，很多内容仍然无法直接映射到标准化输出：版式差异、费用名不统一、AR/AP 主体不明、OCR 把两条费用合并，都会导致字段对不上。

所以系统必须有 `PENDING_REVIEW`：低置信度、规则/LLM 冲突、匹配歧义都先挂起，人工接受、拒绝或修改后再输出。复核结果还可以回流成标注样本，用来优化规则、费用字典和 prompt。**人工不是补丁，而是闭环的一部分。**

---

## 3. 多主体 / 多账套：当前是单一主体，真实业务不会只有一家公司

现在系统默认一个 `ACCOUNTING_ENTITY`，所有 AR/AP 都相对它判断。但真实场景里，同一张 Debit Note，对开单方是 AR，对收单方是 AP；不同分公司、不同账套、不同代理主体，结论都可能不同。

生产化需要：记账主体作为运行参数；主体别名和权限可配置；数据按主体/租户隔离；同一份单据可以按不同主体分别生成操作。**AR/AP 不是单据的属性，是“谁记账”的属性。**

---

## 4. 延迟与并发：本地不用 LLM 也不慢，慢在解析和同步调用

本机实测 `decide` 不走 LLM/OCR：

- PDF2：约 0.24 秒
- PDF1：约 0.38 秒
- EML（含 2 个 PDF 附件）：约 0.56 秒

耗时主要在 `pdfplumber` 解析（单页 PDF 约 263ms / 316ms），抽取、校验、决策本身只有几十毫秒。真正让延迟变大的是：

- `use_llm=true` 时调用火山 Ark，网络往返通常几秒；
- `use_ocr=true` 时 OCR 一次约 10 秒；
- API 同步阻塞，一个请求占一个 worker；
- 每个资产、每条操作单独 commit；
- PDF 页数、EML 附件数量线性增加解析时间。

大系统里应该改成：上传后立即返回 `job_id`，OCR/LLM 放异步队列；worker 有界并发、按租户限流、背压和重试；解析结果按 `sha256` 缓存；PDF 表格按需提取；数据库批量提交。**同步 API 适合演示，异步队列才适合生产。**

---

## 5. 成本控制与成本记录：先能计量，再谈优化

现在 LLM 没有做 usage 输出，所以成本不可见。建议分三步：

1. **记录**：用 LangChain 的 `usage_metadata` 或 `include_raw=True` 拿到 `input_tokens / output_tokens / total_tokens`，落一张 `llm_calls` 表（run_id、model、prompt 版本、token、耗时、是否缓存命中）。
2. **计价**：把模型单价放 `config/pricing.yaml`，按 token 计算每次调用和每份单据的成本。
3. **控制**：设置单次/单租户/单日预算；超预算降级到规则或转人工；按文件 hash 缓存 LLM 结果；只把必要上下文送模型；简单分类用便宜模型，复杂修复再用强模型。

核心原则：**规则优先、LLM 补缺、缓存复用、预算兜底。** 没有 usage 记录，成本优化就是拍脑袋。

---

## 6. 数据安全：资产落库之后，安全边界必须一起设计

票据里有客户名、价格、箱号、银行账号，资产库一旦落盘就涉及安全。生产环境至少要：

- 私有 OSS/对象存储，禁止 public-read；用短有效期签名 URL；
- 访问日志、下载审计、生命周期删除；
- 上传文件类型/大小校验、恶意文件扫描、防路径穿越；
- 日志和 prompt 中脱敏，不把完整银行账号、客户信息发给第三方模型；
- 生产不使用临时公网隧道，改用 VPC/私有端点；

**安全不是部署后补的，是资产库设计的一部分。**

---

## 总结

> 这 6 点分别对应：**数据留得住、异常有人管、主体分得清、系统扛得住、成本算得清、数据守得住。**
> 题目要求的是“能跑通”，真实落地要求的是“能长期跑”。
