# Harness 设计（验收第 8 点）

> 核心立场：**极大程度限制 LLM 的范围和能力。**
> 所有能通过代码规则取到的内容，都不交给 LLM；LLM 只在信息模糊、规则难以判断时，提供自然语言理解和逻辑推理能力。它的输出仍然必须经过校验，并通过人工复核彻底杜绝“模型瞎猜”。

---

## 1. 为什么这个场景需要 Harness

航运账单处理链路里，不确定性来自很多地方：

- 输入格式多：EML、文本 PDF、扫描 PDF、图片、Excel、Word
- OCR 会认错：`0/O`、`1/I`，还可能把多条费用合并
- LLM 会幻觉、漏字段、输出格式不稳定
- 单据版式千变万化
- 匹配可能歧义
- 财务场景错一笔就是事故

因此不能写成“OCR → LLM → JSON”的裸链路，而是要用确定性工程把模型包起来。Harness 的目标不是让模型更聪明，而是**让模型犯错时系统不会跟着错**。

---

## 2. LLM 的边界

| 阶段 | 由谁负责 | 是否使用 LLM |
|---|---|---|
| 文件识别、EML 递归、banner 过滤 | Python + 标准库 | ❌ |
| PDF 文本/表格抽取 | pdfplumber | ❌ |
| Excel/Word 表格 | openpyxl / python-docx | ❌ |
| 图片、扫描件文字/字段识别 | 指定 OCR API | ❌（不是 LLM） |
| 单号、B/L、箱号、日期、金额正则 | Python | ❌ |
| 费用名、币种、付款方式标准化 | YAML 词典 + Python | ❌ |
| 金额/合计/币种校验 | Python | ❌ |
| L1–L4 匹配、增量合并 | Python + SQL | ❌ |
| AR/AP 最终判定 | Python 规则 + LLM 候选 | ⚠️ 部分 |
| 自由文本/模糊版式的语义抽取 | LangChain LLM | ✅ |
| 校验失败后的修复重抽 | LLM | ✅（可选） |
| 人工复核 | `interrupt()` + 人 | ❌ |

一句话：

> **规则负责“能确定的”，OCR 负责“看得见但读不出”的，LLM 只负责“规则看不明白”的。**

---

## 3. 三层闸门

### 3.1 输入闸门

- 扩展名 + magic bytes + MIME 判断类型
- EML 附件递归，`max_depth=3`，`visited` 防循环
- 内嵌 banner/logo 过滤，不送 OCR
- 不支持的格式显式报错，不静默跳过

### 3.2 抽取闸门

- 规则优先：正则、表头映射、OCR 结构化字段
- LLM 补缺：只处理规则抽不到或语义模糊的部分
- 双通道结果合并：规则优先，LLM 补缺，冲突留痕
- 每条费用尽量带 `evidence`，找不到证据的字段降置信度

### 3.3 决策闸门

- Pydantic schema + `extra="forbid"`
- 金额、币种、合计、重复费用、OCR 混淆校验
- L1–L4 匹配，唯一命中才自动处理
- 不唯一、不合法、低置信度 → `PENDING_REVIEW`
- 人工接受/拒绝/修改后才输出最终 JSON

---

## 4. 六个核心机制

### 4.1 规则优先 + 双通道抽取

- 文本 PDF 以本地 `pdfplumber` 文本/表格为主
- 图片/扫描件以 OCR 为主
- LLM 只补规则缺失字段
- 规则和 LLM 冲突不自动裁决

实测例子：PDF2 的 OCR 把两条 `HANDLING CHARGE` 合并成 `100.00`，本地文本保留 `65 + 35`。因此文本 PDF 必须以本地规则为主，OCR 只做交叉校验。

### 4.2 Schema 闸门

- 内部模型：`InternalBillRecord`
- 输出模型：`OutputRecord`，`extra="forbid"`
- 最终写盘前再次校验 JSON Schema
- LLM 通过 `with_structured_output(ExtractionResult)` 直接返回 Pydantic 对象，不解析自由文本

### 4.3 证据与置信度

- 费用名精确命中别名 → `1.0`，模糊/未知 → `0.8`
- 单据置信度：`1.0 - 0.3 × hard - 0.1 × soft`
- LLM 参与时增加三个信号：
  - `llm_confidence`：LLM 自评置信度（弱信号）
  - `llm_evidence_coverage`：有值字段/费用行中带原文证据的比例
  - `extraction_conflicts`：规则与 LLM 的语义冲突
- 低置信度、证据不足、规则/LLM 冲突 → `PENDING_REVIEW`

LLM 自评置信度只作为弱信号，不作为唯一依据；证据覆盖率和规则一致性更重要。

### 4.4 冲突检测

- 标量字段：规则 vs LLM 语义比较（公司名允许中英文括号差异；日期先归一化）
- 费用行：比较数量、金额、币种，而不是只看原始费用名
- 冲突写入 `extraction_conflicts`
- 冲突转为 `EXTRACTION_CONFLICT`（soft + `review_required=True`）

### 4.5 重试、缓存、幂等

- OCR 请求带超时和重试
- OCR 原始响应按 `sha256` 缓存
- 资产按内容指纹去重
- 重复运行不重复建账
- 操作 ID 包含 `run_id`，保留多次运行历史

### 4.6 Checkpoint + 人工闸门

- LangGraph `SqliteSaver` 保存状态
- `interrupt()` 暂停
- `Command(resume=...)` 恢复
- 人工可接受、拒绝或修改字段
- 复核结果写回 `review_items`，最终输出严格 JSON

---

## 5. 为什么这样能提升稳定性与准确性

1. **缩小 LLM 暴露面**：大部分字段由确定性规则产生，模型只处理模糊文本。
2. **规则保留行级明细**：OCR/LLM 可能合并费用行，规则不会。
3. **输出有 schema 闸门**：模型输出不合法直接失败，不会带病入账。
4. **冲突显式化**：规则和 LLM 不一致时，不静默选一个，而是记录并复核。
5. **fail-closed**：不确定就 `PENDING_REVIEW`，宁可慢，不可错。
6. **可追溯**：每个结果都有来源、证据、匹配级别和 audit_trail。
7. **可回归**：黄金用例 + 72 个测试，改代码后能发现行为漂移。

---

## 6. 指标

- 字段级准确率：单据号、金额、币种、费用名
- 操作准确率：CREATE / UPDATE / NO_CHANGE / PENDING_REVIEW
- AR/AP 准确率
- JSON 合法率
- 人工复核率（越低越好，但不能靠自动放行换低）
- 平均耗时、OCR 成功率、LLM 调用成功率

---

## 7. 局限与改进

- 规则关键词/正则目前部分写在 Python 常量里，后续可迁移到 YAML，让业务可维护。
- `.doc` 老格式依赖 LibreOffice；当前环境未安装，只能提示转换。
- LLM 自评置信度校准有限，后续应更多依赖证据覆盖率、规则一致性和黄金集校准。
- `merge_extraction` 的冲突已经能触发人工复核，但冲突分类还可以更细（字段级严重程度）。
- 需要补充更多真实版式和线上回流样本，持续扩充黄金用例。

---

## 8. 结论

> **这个 Harness 的核心不是“让 LLM 更自由”，而是“让 LLM 更受限”。**
> 规则能做的，绝不给 LLM；LLM 能做的，也必须被 schema、规则和人工复核三层约束。
> 在财务场景，**稳定、可审计、可回滚**比“看起来智能”更重要。
